Zusammenfassung & Gesamturteil

solide gut getestet opinionated ✓ Doku-Drift behoben subtile Leak-Vektoren

@spearwolf/signalize ist eine reife, fokussierte und framework-agnostische Reaktivitätsbibliothek auf Basis synchroner Pub/Sub-Eventize-Queues. Die Architektur ist klar, der Code überraschend lesbar (~1.700 LOC Produktion, ~6.700 LOC Tests), und die Suite läuft mit 234 grünen Tests in 7,5 s inklusive expliziter Subscription-Leak-Asserts.

Die fundamentale Mechanik (Effect → Signal-Subscribe-on-Read, RECALL-Re-Run, Batch-Dedup, Priority-Flush, Cleanup-Callbacks, Nested-Effect-Isolation, Recursion-Guard via maxDepth) ist sauber implementiert. Es gibt keinen kritischen Bug und keinen unkontrollierten Memory-Leak — aber zwei strukturelle Leak-Vektoren (orphan SignalGroup ohne explizites clear(); Duplikate in SignalGroup#otherSignals) und einige Doku-/Code-Drifts (peer-dep-Version, ESLint↔Biome, „non-lazy by default”-Test-Name) sollten kuratiert werden.

Empfehlung: Produktionsreif für die explizit beschriebene Zielgruppe (3D-Konfiguratoren, Game-Loops, Dashboards, framework-agnostische Domänen-Logik). Vor v1.0 sollten die unten markierten P1/P0-Punkte adressiert werden.

1. Was macht das Framework?

@spearwolf/signalize liefert vier reaktive Primitive über einem synchronen Eventize-Pub/Sub-Layer:

PrimitivErzeugt viaRolle
SignalcreateSignal()Reaktiver Wert. get() in einem Effect registriert eine Dependency.
EffectcreateEffect()Funktion, die bei Änderung getrackter Signale erneut läuft (synchron, inline).
MemocreateMemo()Gecachtes abgeleitetes Signal — intern: ein Signal, das von einem High-Priority-Effect (Priority 1000) getrieben wird.
Linklink()Explizite One-Way-Datenfluss-Bindung Signal→Signal oder Signal→Callback.

Zusatzschichten: SignalGroup (Lifecycle-Container), SignalAutoMap (Lazy-Map von Signalen), Kontextmodi batch / beQuiet / hibernate, Object-Signals (per Hostobjekt + Name), und TC39-Standard-Decorators @signal/@memo in einem separaten Subpath.

Alleinstellungsmerkmale: kein Scheduler, kein Microtask-Queue, kein virtueller Graph — jede signal.set(x) propagiert inline, bis alle dependent Effects gelaufen sind. Das ist ungewöhnlich (z. B. Solid/Vue batchen implizit) und für deterministisches Verhalten in 3D-/Render-Loops eine bewusste Wahl.

2. Architektur

Reactivity-Flow

1. effect.run()
2. push effect auf globalEffectStack
3. callback() laeuft
4. signal.get() innerhalb des callback
5. signal fragt getCurrentEffect()?.whenSignalIsRead(id)
6. effect subscribed: on(globalSignalQueue, id, priority, RECALL, this)
7. (spaeter) signal value aendert sich:
8. emit(globalSignalQueue, id, newValue)
9. RECALL-Handler im effect feuert -> Schritt 1

Globale Buses

QueueTrägt
globalSignalQueueWert-Änderungen pro Signal-ID
globalDestroySignalQueueSignal-Zerstörung
globalEffectQueueEffect-Lifecycle & RECALL
globalEffectCalledQueueBatch-Deduplication-Tracking

Bewertung

  • stark Minimaler Kern. Vier globale Queues, zwei Wrapper-Klassen (Signal, Effect) über zwei Impl-Klassen (SignalImpl, EffectImpl). Klare Trennung „Public Wrapper ↔ interner Impl“ über die Symbole $signal / $effect.
  • stark Subscribe-on-Read + Cleanup-of-lost-deps ist textbook-sauber: #signals, #lostSignals, #destroyedSignals, #signalSubscriptions halten den State je EffectImpl minimal und werden vor jedem Re-Run bereinigt (siehe EffectImpl.run()).
  • stark Recursion-Guard über EffectImpl.maxDepth = 256 verhindert Stack-Overflows bei self-triggering Effects und wirft stattdessen einen beschreibenden Error.
  • gut Nested-Effect-Isolation: bei jedem Re-Run des Parents werden Child-Effects sauber zerstört, ihre Cleanup-Callbacks laufen, dann werden sie neu erzeugt (Slot-basierter Recycling-Versuch via curChildEffectSlot — siehe unten, kleines Risiko).
  • opinionated Globale Queues = ein einziger Modul-globaler Reaktivitäts-Graph. Mehrere parallele „Reaktivitäts-Welten“ (z. B. SSR-Isolation, Web-Worker-Sandboxing) sind nicht ohne weiteres möglich.
  • Risiko Nested-Effect-Slot-Wiederverwendung in EffectImpl.getCurrentChildEffect(): child effects werden positionell wiederverwendet. Da der Code aber nach jedem run() alle alten Children über destroyChildEffects() aufräumt, wird das Slot-Recycling praktisch nie aktiviert. Effektiv toter Pfad → entweder dokumentieren oder vereinfachen.

Konsistenz-Befunde

P2 Vier Wege, denselben Wert zu lesen

Für ein und dasselbe Signal kann der Konsument lesen via:

  • signal.get()  — getrackt
  • signal.value  — ungetrackt
  • value(signal)  — ungetrackt
  • signal.get(callback)  — deprecated, erzeugt internen Effect

Plus onChange(cb) als Subscription-Variante. Das ist nicht falsch, aber für neue Nutzer verwirrend — vor allem weil beforeRead nur bei getrackten Reads feuert (also nicht bei .value/value()). Empfehlung: einen prominenten „Read-Cheatsheet“-Block ganz oben in der API-Doku.

betrifft: Signal.ts, value.ts, types.ts

P2 set(value, options): zwei Bedeutungen für Funktion-als-Argument

signal.set(fn) speichert die Funktion als Wert (statt — wie React-Nutzer erwarten würden — sie mit dem alten Wert aufzurufen). Nur mit {lazy: true} wird die Funktion als Factory interpretiert. Doku & Tests dokumentieren das explizit, der TypeScript-Typ fängt es im typisierten Pfad ab — aber der häufige React-Reflex „set(v => v + 1)“ produziert bei any-Code eine stille Falle.

betrifft: createSignal.ts:123-158, createSignal.lazy.spec.ts:25-47

P2 String-/Symbol-Dependencies brauchen still attach

createEffect(cb, ['a','b']) ohne {attach: this} würde in EffectImpl-Konstruktor Z. 124 auf group.signal(dep) auflaufen, wo group bereits undefined ist → unkontrollierter TypeError. Implizite Voraussetzung, vom Typsystem nicht erzwungen.

betrifft: EffectImpl.ts:115-134

P3 createMemo-Option name wirkt nur mit attach

Wer nur name setzt (ohne attach) bekommt keine Fehlermeldung, sondern schlicht keine Group-Registrierung. Wäre vom Typsystem als gekoppelter Optionssatz besser ausgedrückt.

betrifft: createMemo.ts:38-49

P3 Static-Deps-Effects haben kein autorun

createEffect(cb, [a,b]) läuft auf Konstruktion nicht automatisch — Konsumenten müssen .run() manuell aufrufen. Das ist dokumentiert, kollidiert aber mit dem Default autorun: true. Klingt nach einem Stolperstein gerade für React-/Vue-Nutzer.

betrifft: EffectImpl.ts:187-192, docs/recipes.md

design Deprecation-Warnungen feuern nur einmal pro Prozess

signalReader(callback) warnt über console.warn exakt einmal — spätere Call-Sites bleiben stumm. Das hält den Output sauber, erschwert aber das Auffinden weiterer Vorkommen. Alternative: pro Call-Site (Stack-Frame-Key) einmal warnen.

betrifft: createSignal.ts:25-33

✓ erledigt @memo()-Decorator ist immer lazy

Doc & Cheat-Sheet sagen das klar. Der Spec-File decorators.memo.spec.ts hat aber den Test-Titel „non-lazy by default“ — das ist irreführend, weil das Verhalten im Test tatsächlich lazy ist (call-count steigt nur bei expliziten Reads nach Mutation). Test-Titel sollte gefixt werden.

betrifft: src/decorators.memo.spec.ts:5

✓ Test-Titel auf 'always lazy' umbenannt.

Stärken

  • Subscription-Leak-Asserts via src/assert-helpers.ts — jedes Spec hat typisch beforeEach/afterEach mit assertEffectsCount(0), assertSignalsCount(0), assertLinksCount(0). Das ist das wertvollste Stück Testinfrastruktur dieses Projekts und würde reaktive Subtilitäten (vergessene Subscribes) sofort fangen.
  • 234 Tests in 7,5 s, alle grün auf der Default-Konfiguration. Eine GC-Spec (SignalGroup.gc.spec.ts, 2 Tests) wird ohne --expose-gc übersprungen (skip-detection korrekt umgesetzt).
  • Async-Effect-Cleanup, Cleanup-on-throw in Batch, maxDepth-Recursion-Throw, Nested-Effect-Cleanup-on-rerun — alles abgedeckt.
  • Edge-Cases dokumentiert und getestet: set(fn)-Updater-Falle, SignalAutoMap.get() nach externem destroySignal, mute/destroy-on-touch.

Gaps

  • Kein Coverage-Report in der CI; Coverage-Tool ist nicht in package.json verdrahtet. Visuell sieht das Verhältnis Test:Prod ~ 4 : 1 aus und die kritischen Pfade (Subscribe, RECALL, Cleanup, Batch-Flush, Nested) sind getestet — formell sollte aber zumindest jest --coverage in pnpm world hängen und ein Mindestwert gefordert werden.
  • Keine Stress-/Property-Based-Tests (z. B. fast-check). Bei einer Bibliothek mit verschachtelten Effects, Priorities und Batches wäre ein PBT-Run lohnend, um zufällige Schedule-Reihenfolgen zu vergleichen.
  • Kein Benchmark-Suite (z. B. tinybench). Für ein Library mit Performance-Anspruch („zero overhead“, „inline propagation“) wäre ein nachvollziehbarer Microbench-Smoke (Signal-set/notify Durchsatz, Memo-Recompute, Batch-Flush-Latenz) wertvoll.
  • Browser-Test-Lauf fehlt. Lib ist Node-First (Engine ≥ 24.13), behauptet aber „runs anywhere modern JS runs“. Ein minimaler Browser-Smoke (z. B. Playwright + Vite-Demo) würde das absichern.

6. Bugs, Memory-Leaks & Risiken

Echte Bugs

Keine identifiziert. Die in v0.28 gefixten Punkte (set(_, {touch:true}) auf muted/destroyed, Batch.run()-Listener-Cleanup im try/finally, SignalGroup-WeakMap-Refactor, EffectImpl.maxDepth) sind im Code & in Tests verankert. Die Suite läuft 234/234 grün.

Strukturelle Leak-Vektoren

P1 Orphan-SignalGroup bei vergessenem clear()

SignalGroup hält in allGroups: Set<SignalGroup> (Z. 18) eine starke Referenz auf jede je erzeugte Group, plus interne #signals/#effects/#links-Sets mit starken Referenzen.

Die Verbesserung in v0.28 (WeakMap<object, SignalGroup> + WeakRef-Store-Key) sorgt zwar dafür, dass das User-Objekt GC-fähig bleibt — aber die Group, ihre angehängten Signale, Effects und deren Subscriptions auf globalSignalQueue leben weiter, solange niemand SignalGroup.delete(obj) aufruft. Die GC des User-Objekts triggert kein automatisches Cleanup; es gibt keinen FinalizationRegistry.

Konsequenz: Wer „komponenten-style“ lebt (createSignal(0, {attach: this})) und in einem unergonomischen Pfad (Exception, Re-Mount, etc.) das explizite SignalGroup.delete(this) vergisst, leakt unbeobachtet. SignalGroup.gc.spec.ts testet nur, dass das User-Object reclaimable wird — nicht, dass die Group selbst aufgeräumt wird.

Vorschlag: Ein optionales FinalizationRegistry-basiertes Auto-Cleanup (mit klaren Caveats über GC-Nicht-Determinismus) oder zumindest ein expliziter Counter getSignalGroupsCount() + Doku-Hinweis, dass attach ohne expliziten Lifecycle-Punkt leakt.

betrifft: SignalGroup.ts:18, :100-106 — keine FinalizationRegistry-Nutzung

P2 SignalGroup#otherSignals akkumuliert Duplikate

attachSignalByName(name, signal) pusht das Signal unbedingt in #otherSignals.get(name) (Array, kein Set). Mehrfaches Attachen desselben Signal+Name-Paares wachsen die Liste — bei 100 Aufrufen entstehen 99 redundante Einträge. Das ist kein Crash, aber bei Hot-Path-Code (z. B. dynamische Bindings auf demselben Namen) ein schleichendes Memory- + Detach-Performance-Problem (detachSignal muss linear über alle Vorkommen iterieren).

Fix: Vor dem Push if (!list.includes(si)) list.push(si); oder Wechsel auf Map<name, Set<SignalImpl>> mit Reihenfolge-Tracking via Array nur wenn ohnehin nötig.

betrifft: SignalGroup.ts:189-193, :243-258

Subtile Risiken

design private constructor()-Trick in SignalGroup

SignalGroup.findOrCreate tut new SignalGroup(object); der Konstruktor nutzt return store.get(object)-Semantik (JS-Konstruktoren dürfen ein Objekt zurückgeben → ersetzt this). Funktioniert, ist aber unkonventionell und durch Biome-Regel noConstructorReturn: "off" erlaubt. Vor Refactorings unbedingt im Hinterkopf.

design Singletons im Modul-Scope

globalSignalQueue, globalEffectQueue, g_objectStores, gLinks, allGroups, der idCreator-Counter sind alle Modul-Singletons. Das ist die bewusste Architektur, hat aber Konsequenzen: Multi-Bundling (z. B. via duplizierte Library-Instances durch verschiedene Resolutions) bricht Reaktivität still — Effects einer Instance können Signals einer anderen Instance nie sehen, weil die Queues nicht geteilt werden. peerDependencies hilft auf npm-Seite, ein Laufzeit-Detect (z. B. globalThis.__signalize__-Sentinel + Warning) wäre Defense-in-Depth.

design signal.value-Getter bei destroyed Signal

Nach destroySignal(s) liefert s.value weiter den letzten Wert, s.set(x) ist ein silent no-op, s.get() trackt nichts. Vorhersehbar und in Docs (recipes.md: SignalAutoMap-Block) erwähnt — aber ohne Warnung bzw. dev-mode-Flag macht das stille Schluck-Verhalten Debugging schwer, wenn ein „toter“ Signal-Lese-Pfad versteckt weiterhin „aktuelle“ Werte zurückgibt.

7. Performance & Skalierbarkeit

Synchrone Inline-Propagation hat klare Vorteile (Determinismus, Game-Loop-Fit, kein Scheduler-Overhead) und klare Trade-offs:

AspektStand
Signal-Read (getrackt) O(1) HashSet-Lookup pro Effect (#signals.has(id)), plus 2 Subscribe-Operationen falls neu. Sehr günstig.
Signal-Write emit() über alle subscribed Effects in Priority-Reihenfolge. Bei 1 Signal → N abhängigen Effects: O(N).
Effect-Re-Run Cleanup-Callback + child-effect-destroy + (für dynamic) lostSignals-Diff. Allokationsarm seit v0.28 (#lostSignals.clear() statt Neuallokation).
Batch-Flush Priority-Insertion-Sort über sehr kleine Listen (typisch N<10). Bei extremem Fan-out (hunderte Effects pro Batch) wäre eine Heap-basierte Variante schneller — irrelevant für die Zielgruppe.
Memo-Update Memo-Effect läuft synchron, Memo-Wert wird in batch() gesetzt — gut für „erst Memo dann Effect“-Semantik.
Symbol-IDs Symbol(`si${n}`) via UniqIdGen wächst unbegrenzt. Bei langlebigen Prozessen mit hohem Signal-Churn ist das kein Leak (Symbols werden GC'd, wenn ihre Map-Keys frei sind), aber die Debug-Beschriftung wird hoch („si1234567“). Kosmetisch.

Skalierbarkeit

  • Sehr gut für UI/Game-Loop-Workloads mit hunderten Signals und tausenden Reads/Writes pro Frame.
  • Solide für Komponenten-Bäume mit Lifecycle-Bündeln (SignalGroup).
  • Grenzwertig bei extrem fan-out-lastigen Szenarien (1 Signal → 10k Effects), weil emit() linear über alle Subscriber läuft.
  • Nicht designed für mehrere isolierte Reaktivitäts-Welten (siehe Singletons-Hinweis oben).

Konkrete Vorschläge

  • Microbench-Suite einführen (tinybench) und für PRs als CI-Schwelle nutzen.
  • In EffectImpl.destroy() wird sechsfach off(...) aufgerufen. Konsolidieren in einen einzigen off(this) wäre prüfenswert, falls Eventize das Subject-Unsubscribe in einem Schritt erlaubt (aktuell explizit für drei Queues + Self).
  • Symbol-ID-Pool je SignalImpl-Klasse wiederverwenden, falls Profile zeigt, dass Symbol-Allokation in Hot-Paths ein Punkt ist.

8. Developer Experience

Was gut funktioniert

  • stark Signal<T>-Klasse wirkt vertraut (.get(), .set(), .value, .onChange()) — Vue/Solid-Nutzer fühlen sich heimisch.
  • stark Lifecycle via SignalGroup + attach: this ist ergonomisch für Komponenten-/Klassen-Style.
  • stark Tooling: Biome (statt ESLint+Prettier) ist schnell, single-binary, klare Konfig. pnpm cbt als „done-gate“ und pnpm world als CI-Match sind klar dokumentiert.
  • stark JSDoc auf praktisch allen Public-Exports → IntelliSense-tauglich.
  • stark getSignalsCount()/getEffectsCount()/getLinksCount() als Debug-Counters — niedrige Hürde, Leaks zu erkennen.

Was hakt

  • friction Node ≥ 24.13 als Mindestversion ist sehr hoch (Node 24 LTS startet Okt 2025). Bibliotheken mit dieser Schwelle werden in Q1 2026 von Bestandsprojekten oft (noch) ausgeschlossen. Ist das gewollt?
  • friction ESM-only + TS 6 sind valide Trends, schließen CJS-Projekte aber komplett aus. Ist für die deklarierte Zielgruppe (3D, PWAs) tragbar.
  • friction Die Multi-Way-Read-API (.get() vs. .value vs. value() vs. .get(cb)) braucht aktive Erklärung. Onboarding-Beispiel ganz oben in der Readme würde helfen.
  • friction Decorators sind im README als „Class API“ prominent, aber TC39-Standard-Decorators werden von TypeScript erst ab v5 stabil unterstützt — ältere Projekt-Setups stolpern.
  • opportunity Es gibt keine offiziellen Integrations-Beispiele (React-Hook-Adapter, Vue-Reactivity-Bridge, Web-Component-Bsp.). Ein examples/-Verzeichnis mit minimalen Demos würde die Adoption stark erleichtern.
  • opportunity Kein DevTools-Inspector (Effect-Graph-Visualizer, Subscription-Heatmap). Wäre für die Debugging-Story ein großer Wert.
